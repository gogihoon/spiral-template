# AI 에이전트 개발 방법론 — v1.1
> Don't be a vibe coder. 위험을 먼저 줄이고, 검증한 만큼만 나아간다.

Spiral 모델을 베이스로, 스크럼의 용어(backlog·spec·daily-log)를 차용한 1인+AI 경량 방법론.

---

## 1. 핵심 원칙

Spiral의 본질은 **risk-driven** — 매 사이클마다 가장 불확실하고 위험한 부분을 먼저 식별·해소하고, 검증된 만큼만 다음으로 나아간다.

AI 개발에서 가장 큰 위험은 **AI가 도메인을 잘못 이해한 채 그럴듯한 코드를 쏟아내는 것**이다. 이를 두 장치로 막는다.

- **도메인 지식(domain.md)** 을 사용자가 먼저 외부화해 판단 기준을 고정한다.
- **스펙 리뷰 게이트** 가 Spiral의 위험 분석 단계다. AI는 함수 단위까지 글로 보고하고, 사용자는 코드를 읽지 않고도 위험을 판단한다.

위험을 **사전에 글로** 줄인 만큼(②), 검증은 **사후에 테스트로** 받아낸다(③). 이 두 축이 짝을 이뤄야 한쪽으로 기울지 않는다. 코딩 실행 규율(가정 명시·단순화·외과적 수정·목표 주도 검증)은 별도 `karpathy-guidelines` 스킬이 담당하며, 이 방법론은 그 위에서 *무엇을 언제 검증할지*의 골격만 정의한다.

## 2. 파일 구조

```
my-project/
├── CLAUDE.md                   세션마다 자동 로드 (프로젝트 컨텍스트 + 규칙)
├── .claude/
│   └── skills/
│       └── karpathy-guidelines/SKILL.md   코딩 실행 규율 (프로젝트 전용 스킬)
└── docs/
    ├── methodology.md          이 문서 (프로젝트 운영 방식)
    ├── domain.md               도메인 지식 (사용자가 가장 먼저 작성)
    ├── requirements.md         기능(FR)·비기능(NFR) 요구사항
    ├── backlog.md              기능 목록 및 우선순위
    └── features/[기능명]/
        ├── spec.md             설계 문서 (구현 전 작성·승인, 위험·함수·검증 포함)
        └── daily-log.md        해당 기능 작업 기록
```

프로젝트 시작 시 **domain → requirements 순서로 먼저 채운다.** 코딩 실행 규율(가정 명시·단순화·외과적 수정·tests-first)은 `.claude/skills/karpathy-guidelines` 스킬이 담당하며, 구현 작업 시 자동 로드된다.

## 3. Spiral 사이클 — 기능 1개 = 나선 한 바퀴

```
        ┌─────────────────────┬─────────────────────┐
        │ ① 목표 결정          │ ② 위험 분석          │
        │ (Determine          │ (Identify & Resolve  │
        │  objectives)        │  risks)              │
        │                     │                      │
        │ requirements.md에서  │ domain.md 기준으로    │
        │ 이번 기능·완료 기준   │ 불확실/위험 지점 식별  │
        │ 선택                 │ → 스펙 작성 → 리뷰 게이트│
        ├─────────────────────┼─────────────────────┤
        │ ④ 다음 사이클 계획   │ ③ 개발 및 검증        │
        │ (Plan next)         │ (Develop & Verify)   │
        │                     │                      │
        │ daily-log 기록 +     │ 승인된 스펙대로 구현   │
        │ backlog 동기화 +     │ → 사용자가 직접        │
        │ git commit          │ 실행·검증            │
        └─────────────────────┴─────────────────────┘
                  나선이 바깥으로 커지며 완성도 상승
```

| 사분면 | 담당 | 산출물 / 행동 |
|---|---|---|
| ① 목표 결정 | 나 | requirements.md에서 기능 1~2개 선택, 완료 기준(DoD) 명시. 새 아이디어는 backlog에만 추가 |
| ② 위험 분석 | AI→나 | AI가 spec.md 작성(위험 블록 + 함수 명세 + 검증 계획) → 사용자가 도메인 기준으로 리뷰·승인. 스펙을 막는 불확실성이 *코드로만* 풀리면, 추측하지 말고 최소 코드로 먼저 확인 후 사실을 스펙에 반영 |
| ③ 개발 및 검증 | AI→나 | 승인된 스펙대로 구현하고, DoD를 테스트로 번역해 통과시킨다(tests-first) → 사용자가 직접 실행·확인. 실패 시 ②로 복귀 |
| ④ 다음 계획 | AI/나 | daily-log 업데이트 + backlog 동기화 + commit → 다음 나선 결정 |

**② 위험 분석이 이 방법론의 심장이다. 글로 검증하는 이 단계를 건너뛰면 바이브 코딩과 다를 게 없다.**

## 4. 도메인 지식 (`domain.md`)

위험을 판단하려면 기준이 필요하다. AI가 아니라 사용자가 직접 쓴다. 짧아도 된다.

```markdown
# 도메인 지식

## 이 프로젝트가 다루는 것
(한 문단. 무엇을, 누구를 위해, 왜)

## 핵심 용어
| 용어 | 정의 | 비고 |
|---|---|---|

## 도메인 규칙 (반드시 지켜야 하는 제약)
- (예: 주문은 결제 완료 전엔 절대 확정되지 않는다)
- (예: 사용자 잔액은 음수가 될 수 없다)

## 흔한 오해 / AI가 틀리기 쉬운 지점
- (직관과 다른 부분을 미리 적어두면 위험 분석이 쉬워진다)
```

## 5. 요구사항 (`requirements.md`)

```markdown
# 요구사항

## 기능 요구사항 (FR)
| ID | 요구사항 | 우선순위 | 완료 기준(DoD) |
|---|---|---|---|
| FR-1 | 사용자는 이메일로 로그인할 수 있다 | High | 잘못된 비번 시 에러 메시지 표시 |

## 비기능 요구사항 (NFR)
| ID | 항목 | 기준 |
|---|---|---|
| NFR-1 | 성능 | 응답 95%ile < 300ms |
| NFR-2 | 보안 | 비밀번호 해싱(bcrypt 이상), 평문 저장 금지 |
| NFR-3 | 확장성 | 동시 접속 1,000 가정 |
| NFR-4 | 가용성/에러 | 외부 API 실패 시 graceful degradation |
```

① 목표 결정에서 이 ID를 골라 사이클을 시작하고, spec.md는 항상 어떤 FR/NFR을 만족시키는지 명시한다.

## 6. AI 보고 양식 (`spec.md`)

spec.md는 아래 세 블록을 반드시 포함한다. 구현 전에 글로 먼저 보고한다.

### 6-1. 위험 / 불확실성
이 기능에서 가장 불확실한 것을 먼저 적는다. 리뷰 게이트가 어디를 집중해서 볼지 정하는 기준이 된다.

```markdown
## 위험 / 불확실성
| 위험 | 검증 방법 | 코드로만 확인 가능? |
|---|---|---|
| 외부 API가 빈 응답을 줄 때 동작 | 스펙 리뷰로 합의 | 아니오 |
| Basic Pitch가 디스토션 기타 음정을 따는가 | 최소 코드로 먼저 확인 | 예 (스펙 전 확인) |
```

> "코드로만 확인 가능"이 예이면, 추측으로 스펙을 쓰지 말고 최소 코드로 사실을 먼저 확인한 뒤 그 결과를 아래 설계에 반영한다. 확인용 코드는 사실만 남기고 버린다.

### 6-2. 설계 개요
```markdown
## 대상 요구사항
FR-2, NFR-1

## 구현 방식과 이유
(왜 이 접근을 택했는가 + 검토했지만 버린 대안)

## 파일/컴포넌트 구조
(어떤 파일이 새로 생기고/바뀌는가)

## 엣지케이스
- ...

## 이번에 하지 않을 것
- ...
```

### 6-3. 함수 명세
주요 함수마다 아래를 보고한다. 코드는 아직 쓰지 않는다.

```markdown
### `함수명(params) -> 반환타입`

- 역할: 한 문장으로 이 함수가 하는 일
- 입력:
  | 인자 | 타입 | 제약 / 유효범위 |
  |---|---|---|
  | userId | string | 비어 있을 수 없음, UUID 형식 |
  | amount | int | > 0 |
- 출력: 타입과 의미 (예: `Result<Order, Error>`)
- 예외 / 에러 케이스: 어떤 입력에서 무엇을 던지거나 어떻게 처리하는가
- 부작용(side effect): DB 쓰기, 외부 API 호출, 상태 변경 등
- 호출 관계: 이 함수가 호출하는 것 / 이 함수를 호출하는 것
```

목적: ① 사용자가 코드를 읽지 않고 입출력·예외만 보고 설계 결함을 잡는다. ② 함수 단위 설계 근거를 읽으며 AI를 학습 도구로 쓴다.

### 6-4. 검증 계획
①의 DoD와 6-1의 위험을 **테스트 케이스로 번역**한다. ③ 개발 단계는 이 테스트를 통과시키는 것으로 완료를 판정한다(tests-first). 이 블록이 있어야 "검증한 만큼만 나아간다"가 실제로 작동한다.

```markdown
## 검증 계획
| 검증 대상 (DoD/위험) | 테스트 케이스 | 기대 결과 |
|---|---|---|
| FR-1 잘못된 비번 처리 | 틀린 비밀번호로 로그인 시도 | 401 + 에러 메시지 |
| 외부 API 빈 응답 (위험) | 빈 응답 목(mock) 주입 | 예외 없이 fallback 반환 |
```

## 7. 적용 가이드

**적합한 상황**

| 상황 | 이유 |
|---|---|
| 1인 또는 소규모 사이드 프로젝트 | 팀 없이도 체계적으로 개발 가능 |
| AI를 쓰면서 실력도 키우고 싶을 때 | 함수 명세 리뷰가 그대로 학습 도구가 됨 |
| 여러 환경에서 끊어서 작업할 때 | 문서 체계로 세션 종료 후 컨텍스트 즉시 복원 |
| 도메인이 까다롭고 AI가 자꾸 헛다리 짚을 때 | domain.md + 위험 분석 사분면이 정확히 이 문제를 겨냥 |

**맞지 않는 상황**

| 상황 | 이유 |
|---|---|
| 빠르게 만들고 버릴 프로토타입 | 스펙 작성·리뷰 비용이 속도를 늦춤 |
| 대규모 팀 프로젝트 | 팀 단위 협업 도구와 프로세스가 따로 필요 |
| 도메인 지식이 전혀 없는 분야 | domain.md를 채울 수 없으면 위험 분석 자체가 불가능 |

## 8. 명령어 모음

### 프로젝트 시작
```
docs/domain.md 양식 보여줘. 내가 도메인 지식 채울게.
다 채우면 그걸 기준으로 requirements.md 초안 같이 만들자.
```

### 세션 시작
```
오늘 할 것: [기능명] (FR-X)
docs/domain.md, docs/requirements.md, docs/features/[기능명]/ 폴더,
backlog.md 읽고 현황이랑 이번 사이클 목표 요약해줘.
```

### 스펙 작성 요청 (② 위험 분석)
```
[기능명](FR-X, NFR-Y) 구현 전에,
docs/features/[기능명]/spec.md에 설계 스펙만 먼저 작성해줘.

포함:
- 위험/불확실성 (가장 불확실한 것 + 검증 방법, 코드로만 풀리는지)
- 대상 요구사항(FR/NFR ID)
- 구현 방식과 이유 (+ 버린 대안)
- 파일/컴포넌트 구조
- 엣지케이스 / 이번에 안 할 것
- 주요 함수마다: 시그니처 / 입력(타입·제약) / 출력 / 예외 / 부작용 / 호출관계
- 검증 계획 (DoD·위험을 테스트 케이스로 번역)

코드로만 확인되는 불확실성이 있으면, 추측으로 스펙 쓰지 말고 최소 코드로 먼저 확인하고 결과를 반영해줘.
domain.md 규칙에 어긋나는 가정이 있으면 명시적으로 표시해줘.
구현은 내가 검토·승인한 뒤에 시작해.
```

### 구현 (③)
```
스펙 확인했어. 함수 명세대로 구현하고, 검증 계획의 테스트부터 작성해서 통과시켜줘.
스펙(특히 입출력·예외) 벗어나는 부분 생기면 먼저 말해줘.
```

### 세션 종료 (④)
```
오늘 작업 docs/features/[기능명]/daily-log.md에 추가해줘.
- 완료한 것 (어떤 FR/NFR 충족했는지)
- 결정 사항과 이유
- 남은 위험 / 다음 사이클 할 것

backlog.md 완료 항목 체크하고 동기화해줘.
```

### 컨텍스트 리셋 (70% 도달 시)
```
지금까지 작업을 daily-log.md에 중간 기록으로 저장해줘.
꼭 포함:
- 변경한 파일 목록
- 결정한 것과 이유
- 해결 못 한 문제 / 남은 위험
```
저장 후 `/clear` → 새 세션에서 `"daily-log.md 읽고 이어서 진행해줘"`

## 9. 스크립트

### 프로젝트 초기 세팅
```bash
#!/bin/bash
mkdir -p docs/features .claude/skills/karpathy-guidelines
touch CLAUDE.md \
      docs/methodology.md \
      docs/domain.md \
      docs/requirements.md \
      docs/backlog.md \
      .claude/skills/karpathy-guidelines/SKILL.md
echo "완료. 다음 순서로 채울 것:"
echo "  1) docs/domain.md       (도메인 지식 — 직접 작성)"
echo "  2) docs/requirements.md (FR/NFR)"
echo "  3) CLAUDE.md            (기술 스택 + 규칙)"
echo "  + .claude/skills/karpathy-guidelines/SKILL.md 에 코딩 규율 채우기"
```

### 새 기능 시작
```bash
#!/bin/bash
FEATURE=$1
mkdir -p docs/features/$FEATURE
touch docs/features/$FEATURE/spec.md
touch docs/features/$FEATURE/daily-log.md
echo "docs/features/$FEATURE 생성 완료"
echo "backlog.md에 추가: - [ ] $FEATURE (FR-?) -> docs/features/$FEATURE/"
```
